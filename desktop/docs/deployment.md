# Deploying the composer desktop

The desktop ships as a self-contained application for Linux and Windows:
the Electron shell, the built Angular renderer, and the composer server
with its embedded SurrealDB engine bundled into the app's resources. No
Node.js, no checkout — install and run; the gateway spawns the bundled
server on first attach (the usual probe → spawn-on-refusal flow).

## Build

From `desktop/` (npm-managed; the workspace root is pnpm):

```sh
npm install          # once
npm run dist:linux   # AppImage + deb  → release/
npm run dist:win     # NSIS setup.exe  → release/
npm run dist         # whatever the host builds (both on Linux: AppImage, deb, NSIS)
```

Each script runs the Angular build, stages the server
(`scripts/prepare-server.mjs`), then invokes electron-builder
(`electron-builder.yml`). Windows NSIS builds fine from Linux unsigned —
electron-builder edits the exe resources with resedit (no wine); code
signing is not configured yet.

Outputs land in `desktop/release/` (gitignored):

- `composer-<version>.AppImage` / `composer-<version>.deb`
- `composer-setup-<version>.exe` (+ `.blockmap` for delta updates later)

## What ships, and where it runs from

- `app.asar` — `electron/` (main, preload, gateway) and
  `dist/composer-desktop/browser/` (the renderer).
- `resources/server/index.mjs` — the server as one esbuild bundle; its
  native SurrealDB engine (`@surrealdb/node`) is baked into the bundle
  with the platform `.node` binaries beside it.
  `scripts/prepare-server.mjs` trims the bindings to
  `linux-x64-gnu, linux-x64-musl, win32-x64-msvc, win32-arm64-msvc`
  (override with `COMPOSER_BINDINGS=a,b`).
- `resources/icon.png` — generated by `scripts/make-icons.mjs`
  (deterministic, no image tooling; also writes `build/icon.ico`/`png`).

Packaged runtime paths (set by `electron/main.js`):

- Server entry: `process.resourcesPath/server/index.mjs`
  (`COMPOSER_SERVER_ENTRY`).
- Gateway spawn record + server log: the Electron `userData` dir
  (`COMPOSER_SPAWN_RECORD`, `COMPOSER_SERVER_LOG`) — the app bundle is a
  read-only asar, so the dev checkout's `desktop/logs/` defaults never
  apply.
- Server data: the platform default from `server/src/index.ts` — XDG
  (`~/.local/share/composer-v2`) on Linux, `%APPDATA%\composer-v2` on
  Windows — unless `COMPOSER_DATA_DIR` says otherwise.
- The gateway spawns the server as plain Node
  (`ELECTRON_RUN_AS_NODE=1`): in an installed app `process.execPath` is
  the composer binary itself, which must not boot a second GUI.

The single-instance lock only engages in packaged builds — dev
checkouts keep running multiple instances side by side.

## Attach-only deployments still work

`COMPOSER_SERVER_URL` (and `COMPOSER_SERVER_CMD` for the WSL-style
spawn) behave exactly as in dev: point them before launching and the
gateway attaches instead of spawning, or never spawns when no local
entry applies.

## Known limits

- No code signing (Windows SmartScreen will warn; macOS is out of
  scope).
- `oneClick: false` — the NSIS installer lets the user pick the
  directory.
- The renderer's CSP is baked into `dist/.../index.html`; nothing
  config-level to do at package time.
